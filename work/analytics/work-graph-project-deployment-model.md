# AN-40: Модель развёртывания Work Graph на проект — встроенный, консоль-хост или гибрид

**Запрос:** «Проанализируй пользовательский опыт развёртывания похожих проектов на Work Graph. Как было бы удобно установить WG, чтобы подключить его к проекту: должна ли это быть установка WG внутрь проекта, или из WG нужно заводить проект в UI и потом переключаться между ними?»

## Кратко

Сегодня WG — **один инстанс на один репозиторий**: канон (`intent/`, `charter/`, `architecture/main.bvc`) читается относительно собственного корня WG, UI поднимается из cwd. Это удобно, когда Work Graph обслуживает **свой же** репозиторий, но плохо масштабируется на **несколько похожих проектов** (несколько OneBase-конфигураций, несколько Marketplace-вертикалей): N установок = N портов, N апдейтов движка, N разрозненных UI.

**Рекомендация — гибрид (вариант C):**

1. **Канон живёт внутри проекта** (`intent/`, `charter/`, `architecture/main.bvc`, `.work-graph/`) — это единый источник правды, версионируется вместе с кодом, агент в этом репо читает его локально.
2. **Движок WG ставится как инструмент** (`npx @work-graph/cli`, dev-зависимость), а не как форк всего репозитория WG.
3. **WG-консоль (хост) монтирует один или несколько корней проектов** и переключается между ними в UI; «проект» в UI = лёгкая запись-указатель (путь + опц. git remote), а не отдельное хранилище.

Это совпадает с тем, **как уже устроены домены** (OneBase и Marketplace федерируются как под-домены внутри одного WG — см. вариант A в AN-39) и с уже существующим прецедентом **указателя на внешний корень** (`resolveOnebaseMetadataScanRoot`, sidecar `projectCwd`).

## 1. Как устроено сейчас (факты из кода)

| Аспект | Где | Поведение |
|---|---|---|
| Корень канона | `src/architectureL1Canon.mjs` → `ARCHITECTURE_L1_CANON_REPO_ROOT = join(moduleDir, '..')` | Канон читается **относительно репо WG**, не из произвольного проекта |
| Backlog UI | `src/workGraphBacklogUiServer.mjs`, `npm run backlog:ui` | Поднимается из cwd, порт **4177** жёстко; читает `intent/`, `architecture/main.bvc` своего репо |
| Один WG на репо | [AN-20 §6.2](ux-current-state-and-vector.md) | Явно: «Переключатель нескольких рабочих областей — у нас один Work Graph на репо», «projects → workspaces избыточно для одного репо» |
| Внешний проект (OneBase) | `src/onebaseCliCapabilityProbe.mjs` → `ONEBASE_PVRG_METADATA_SCAN_CANDIDATES = ['tests/fixtures/onebase', '../onebase/examples/trade', 'domains/onebase/examples/trade']` | WG уже умеет **указывать на чужой корень** по относительному пути / `projectRoot` / env |
| Sidecar на проект | [AN-17 §2](onebase-integration-vertical-stack.md) | `projectCwd → examples/trade`, `ONEBASE_API_BASE_URL`, read-only PG profile — указание на внешний проект через env |
| Домены как федерация | [AN-39](architecture-domains-l1-hierarchy.md) + вариант A | OneBase / Marketplace уже живут как **под-домены L2 одного WG**, не как отдельные инсталляции |

**Вывод:** механика «указать WG на внешний корень» уже частично есть (для OneBase metadata и sidecar), но **управляющий канон WG (intent/charter/architecture) всё ещё привязан к собственному репо**. Для «похожих проектов» это и есть точка боли.

---

## 2. Что значит «развернуть WG на похожий проект»

Пользовательский сценарий: есть N однотипных проектов (например, три OneBase-конфигурации заказчиков, или Marketplace-вертикали classified/freelance/wellness из AN-MP-1). Для каждого нужно: backlog, intent-граф, architecture map, agent-runtime, trace/evidence.

Ключевой вопрос разбивается на два независимых:

- **Q1. Где живёт канон проекта** (intent/charter/architecture/work-items)?
- **Q2. Где живёт UI/консоль оператора** и как он видит несколько проектов?

Эти ответы **ортогональны** — именно их смешение порождает ложную дилемму «внутрь проекта ИЛИ заводить в UI».

---

## 3. Три модели развёртывания

### Вариант A — Встроенный в проект (WG внутрь проекта)

`work-graph init` создаёт в целевом проекте `intent/`, `charter/`, `architecture/main.bvc`, `.work-graph/config.json`; движок — npx CLI / dev-зависимость; UI запускается из проекта.

| + | − |
|---|---|
| Канон версионируется с кодом, едет в git | N проектов = N установок движка, N апдейтов |
| Агент в репо читает канон локально, офлайн | N UI на N портах → коллизии (как 4177 EADDRINUSE) |
| Нет единая точка отказа | Нет общего обзора «все проекты сразу» |
| Простая модель прав (репо = граница) | Дублирование протоколов/скриптов/lint между проектами |

### Вариант B — Консоль-хост (заводить проект в UI, переключаться)

Один автономный инстанс WG; проекты регистрируются записями в UI, канон лежит в хранилище хоста; переключение проектов в шапке.

| + | − |
|---|---|
| Один UI, один порт, общий обзор N проектов | Канон оторван от кода проекта (расхождение, отдельный резервная копия) |
| Один движок — один апдейт | Агент в репо проекта не видит канон без обращения к хост |
| Кросс-проектная аналитика/метрики из коробки | Мультитенантный права, изоляция — сложнее |
| Удобно для PM/оператора | Противоречит «канон = открытый формат рядом с кодом» (AN-8) |

### Вариант C — Гибрид (рекомендация)

Канон **в репо проекта** (как в A) + WG-хост **монтирует корни проектов и переключается** (как в B), читая их канон в репозитории. «Проект» в UI = указатель (path + опц. remote), не копия данных.

| + | − |
|---|---|
| Единый источник правды в коде, едет в git, агент читает локально | Нужен реестр проектов + переключатель проектов (новый код) |
| Один UI/хост для N проектов, общий обзор | Хост должен резолвить разные корни (есть прецедент `resolveOnebaseMetadataScanRoot`) |
| Движок — один (CLI/хост), канон — распределённый | Кросс-проектная аналитика — отдельный слой агрегации |
| Совпадает с федерация доменов (AN-39 вариант A) | — |

---

## 4. Почему C, а не A или B

1. **Канон обязан быть в репо.** Агент, который правит код проекта, читает `intent/`/`charter/` из рабочего репозитория (эталонный сценарий в README: `charter.bvc → Work Graph task → agent claim → trace`). Если канон в host'е (вариант B) — агент в репо его не видит без сети, и нарушается принцип «открытый формат рядом с кодом» (AN-8). → **Q1 = в проекте.**

2. **UI на проект не масштабируется.** Чистый встроенный вариант (вариант A) для N похожих проектов даёт N портов и N апдейтов; мы уже ловили `EADDRINUSE: 127.0.0.1:4177` при двух инстансах. Оператору нужен **один хост с переключателем**. → **Q2 = хост с переключателем.**

3. **Прецедент уже в коде.** `resolveOnebaseMetadataScanRoot({ repoRoot, relativeRoot })` и sidecar `projectCwd` уже резолвят внешний корень. Режим хоста — обобщение этого механизма с одного OneBase-пути на список зарегистрированных проектов.

4. **Совпадает с федерация доменов.** В AN-39 (variant A) OneBase и Marketplace стали L2-под-доменами одного WG. Гибрид просто поднимает эту же идею на уровень выше: домены внутри проекта, проекты внутри хоста.

## 5. Целевой UX (вариант C)

### 5.1. Установка на новый проект (сначала через CLI)

```bash
cd my-onebase-config
npx @work-graph/cli init          # каркас intent/ charter/ architecture/main.bvc .work-graph/
npx @work-graph/cli ui            # поднять локальный UI ИЛИ:
work-graph register .             # зарегистрировать корень в общем host
```

`.work-graph/config.json` в проекте: `{ "schema": "...", "projectId": "...", "domains": [...], "canonRoot": "." }`.

### 5.2. Реестр проектов (хост)

`~/.work-graph/workspaces.json` — список `{ projectId, root, remote?, lastOpened }`. Host резолвит канон каждого через тот же путь, что и `ARCHITECTURE_L1_CANON_REPO_ROOT`, но **параметризованный repoRoot** (он уже принимается как `options.repoRoot` в `loadArchitectureL1Canon`).

### 5.3. Переключатель проектов в UI

Шапка сайдбара: текущий проект + dropdown «переключить / добавить корень». Cmd+K скоуп `project:` (созвучно палитре из AN-20 §5.4). Переключение = сменить `repoRoot`, перечитать snapshot — **без перезапуска сервера**.

### 5.4. Что переиспользуется

- `loadArchitectureL1Canon(repoRoot, options)` уже принимает `repoRoot` → достаточно прокинуть его из реестра.
- `buildOnebasePvrgGraphFromProjectRoot({ repoRoot, projectRoot })` уже параметризован.
- Снимок (`buildArchitectureSnapshot`) — сделать `repoRoot`-aware (сейчас неявно cwd).

## 6. Минимальные изменения для перехода к C

| Шаг | Файл / зона | Суть |
|---|---|---|
| 1 | `src/workGraphBacklogUiServer.mjs` | Параметр `repoRoot` (env `WG_PROJECT_ROOT` / query), убрать неявный cwd; порт из конфига |
| 2 | новый `src/workspaceRegistry.mjs` | Чтение/запись `~/.work-graph/workspaces.json`, резолв корней |
| 3 | новый `packages/work-graph-cli` | `init`, `register`, `ui` поверх существующих движков |
| 4 | UI | Переключатель проектов в шапке + Cmd+K скоуп `project:` |
| 5 | `src/architectureSnapshot.mjs` | Сделать snapshot полностью `repoRoot`-aware (не cwd) |
| 6 | docs | Runbook «развернуть WG на новый проект» |

Все «движковые» функции (`loadArchitectureL1Canon`, onebase graph) **уже** принимают `repoRoot`/`projectRoot` — основная работа на UI-server и реестре, не в ядре.

## 7. Риски и митигации

| Риск | Митигация |
|---|---|
| Хост читает чужие корни → утечка/права | Для одного арендатора pilot; реестр только локальный; явный `register` |
| Drift версии канона между проектами | `.work-graph/config.json` хранит `canonSchemaVersion`; хост предупреждает |
| Разные версии движка vs канон проекта | CLI пинит совместимый диапазон; `init` пишет версию |
| Переключение проекта теряет состояние UI | Per-project `localStorage` namespace (сохранённые представления из AN-20) |
| Порт-коллизии при локальном `ui` на проект | Host по умолчанию один порт; локальный `ui` берёт свободный порт |
| AN-20 ранее отверг multi-workspace | Контекст изменился: тогда «один репо»; теперь явный кейс «похожие проекты» → пересмотр оправдан |

---

## 8. Что НЕ делать

- Не переносить канon в централизованное хранилище хоста (ломает agent-local чтение и AN-8).
- Не делать форк всего репо WG на каждый проект (дублирование движка).
- Не строить мультитенантный authn/permissions для пилота (для одного арендатора достаточно).
- Не плодить по UI-серверу на проект — один хост с переключателем.

---

## 9. Вердикт

«Внутрь проекта» **или** «заводить в UI» — ложная дилемма. Правильно **и то, и другое по своей оси**:

- **Канон** — внутрь проекта (в git, читается агентом локально).
- **Консоль оператора** — один host, который монтирует корни проектов и переключается между ними.

Движок WG к этому уже почти готов (функции принимают `repoRoot`/`projectRoot`); не хватает **реестра проектов + переключатель проектов в UI + CLI `init`/`register`**. Это естественное продолжение федерация доменов из AN-39 и центр-управления из AN-20.

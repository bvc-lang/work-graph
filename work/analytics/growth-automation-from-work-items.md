# AN-74: Автоматизация продвижения из задач — что ИИ сделает сам, что нет

**Запрос:** составь анализ продвижения — что сможет AI сделать сам (регистрация на площадках, написание и публикация статей, общение в комментариях и т.д.), чтобы процесс был автоматизированным из созданных задач; сохрани анализ в разборы.

> Разбор реалистичный, а не «маркетинг по кнопке». Главный честный тезис: **ИИ автоматизирует производство и доставку контента, но не подмену человека/аккаунта**. Регистрация на площадках, масс-комментинг и «накрутка» либо технически блокируются (CAPTCHA, верификация телефона, анти-бот), либо запрещены ToS и ведут к банам и репутационному ущербу. Автоматизировать нужно безопасную часть, а распространение держать на официальных API + human-in-the-loop.

## 0. Контекст: на что опирается автоматизация в этом проекте

В Work Graph уже есть машинерия, на которую ложится «продвижение из задач»:

- **Конвейер канона:** `analytics (AN) → epic → backlog → board → closing-анализ` (`protocols/decision-pipeline-canon`). Промо — это просто новый домен задач в этом конвейере.
- **Agent worker loop** (`src/agentWorkerLiveLoop.mjs`): `claim → Worker Input → Worker Output (patch/evidence) → transition`. Может исполнять задачи провайдером (local/openai) с записью свидетельств.
- **Cursor Automations** (скилл `automate`): триггеры `cron` / `git PR` / `webhook` + промпт агента + MCP-действия. Это и есть «планировщик» для регулярного промо (еженедельная статья, релиз → анонс).
- **Cursor SDK** (`@cursor/sdk`): headless-запуск агентов из CI/скриптов — для пакетной генерации/публикации.
- **MCP-сервер** (`@work-graph/mcp`): агент читает/обновляет задачи и пишет evidence.
- **Каналы, которые уже есть:** сайт `workgraph.ru`, npm (`@work-graph/*`, `@bvc-lang/*`), GitHub-репозитории, публичный сайт с `/llms.txt` и docs.

Отдельного маркетинг/growth-домена в репозитории **нет** — это проектируемый слой.

## 1. Три уровня автоматизации (ключевая рамка)

| Уровень | Что значит | Кто исполняет | Риск |
|---|---|---|---|
| **A. Полная авто** | ИИ делает от и до без человека | agent worker / Automation | низкий — только для генерации артефактов и публикации через **свои** API-ключи |
| **B. Авто с подтверждением** | ИИ готовит и ставит в очередь, человек жмёт «опубликовать» | agent + approval gate | средний — публикация в публичные каналы под брендом |
| **C. Только человек** | ИИ не имеет права действовать сам | человек (ИИ максимум черновик) | высокий — регистрация, комменты, DM, всё против ToS |

**Правило проекта:** по умолчанию всё новое промо-действие — уровень **B**, пока канал и метрики не доказаны. Уровень **A** — только для генерации и для платформ с официальным write-API на ваших ключах. Уровень **C** не автоматизируется никогда.

## 2. Что ИИ реально сделает сам (уровень A — безопасно)

Это «производственный цех» — здесь автоматизация даёт максимум пользы при нулевом ToS-риске:

- **Контент:** статьи/туториалы (RU+EN), сравнения с конкурентами (есть основа: AN-70 vs Spec Kit), кейсы, README/quickstart, changelog/release notes, FAQ, `llms.txt`, doc-страницы, SEO-лендинги, посты для соцсетей (нарезка из одной статьи в твит-тред/LinkedIn/Telegram-пост).
- **Ассеты:** диаграммы (Mermaid уже в стеке), скриншоты UI (через browser-инструменты), OG-картинки, короткие GIF/демо-сценарии, JSON-LD/Schema.org разметка.
- **Локализация:** перевод RU↔EN (целевые аудитории: 1С/OneBase = RU, общий dev = EN).
- **Дистрибутивные пакеты:** готовый «submission kit» под каждую площадку (заголовок, тело, теги, канонический URL, картинка) — чтобы публикация была одним API-вызовом или одной вставкой.
- **SEO/находимость:** sitemap, meta, внутренняя перелинковка, обновление awesome-list PR (через git), llms.txt для агентов.
- **Аналитика и отчётность:** сбор метрик по опубликованному (звёзды GitHub, npm downloads, просмотры статей через API площадок), еженедельный дайджест, генерация closing-анализа эпика промо.

## 3. Что ИИ сделает «полу-сам» — публикация через официальные API (уровень B)

Публикация **под вашим аккаунтом** через официальный write-API + ваш токен. ИИ генерирует и отправляет, человек один раз подтверждает (или доверяет каналу после N успешных публикаций).

| Площадка | Офиц. write-API | Авто-публикация реальна? | Режим |
|---|---|---|---|
| **GitHub** (releases, Discussions, issues, awesome-PR) | да (REST/GraphQL) | да | A/B |
| **npm** (publish, README) | да (CLI/token) | да (уже есть `publish:work-graph-npm`) | A |
| **Dev.to / Forem** | да (Articles API) | да | B |
| **Hashnode** | да (GraphQL API) | да | B |
| **Telegram-канал** | да (Bot API) | да | A/B |
| **Mastodon / Fediverse** | да (REST API) | да | B |
| **X / Twitter** | да, но платный и лимиты | частично | B |
| **LinkedIn** | ограниченный (Marketing API, модерация) | сложно | B/C |
| **Reddit** | API есть, но жёсткий анти-спам/карма | рискованно | C (черновик) |
| **Hacker News / Lobsters** | публикация только вручную | нет | C (черновик + тайминг) |
| **Habr / VC.ru** | нет публичного publish-API | нет | C (черновик, ручная вставка) |
| **Product Hunt** | API для чтения; запуск — вручную | нет | C (подготовка лонча) |
| **YouTube** | Data API (upload) | да (если есть видео) | B |
| **Email/newsletter** (Buttondown/Resend и т.п.) | да | да | A/B |

**Вывод:** реальный «авто-публикуемый» костяк для dev-инструмента — **GitHub + npm + Dev.to + Hashnode + Telegram + Mastodon (+ X)**. Остальное (Habr, HN, Reddit, Product Hunt) — ИИ готовит черновик и тайминг, публикует человек.

## 4. Что ИИ НЕ сделает сам (уровень C — честно про ограничения)

- **Регистрация аккаунтов на площадках.** Почти везде: CAPTCHA, подтверждение телефона/почты, анти-бот, а ToS прямо запрещают автоматическую регистрацию. Браузерная автоматизация для обхода = баны + нарушение правил. **Аккаунты заводит человек один раз**, дальше ИИ работает через выданные API-токены.
- **Массовые комментарии / ответы в тредах / DM-аутрич.** Технически возможно, но это **спам**: бан аккаунтов, теневой бан, репутационный ущерб, во многих юрисдикциях — нарушение правил платформ. ИИ может *черновить* ответ на конкретный вопрос, но постить должен человек (или строго рейт-лимитированный уровень B на *своих* каналах поддержки).
- **«Накрутка» (фейковые звёзды/апвоты/отзывы, астротурфинг).** Запрещено, обнаруживается, токсично для бренда. Не делать.
- **Публикация под чужой/анонимной личиной, обход гео/анти-фрод.** Не делать.

> Критическая связка с AN-73: продвигать ИИ-спамом **непровалидированный** продукт без пользователей — это усиление главного риска проекта (рост площади без подтверждения спроса). Сначала контент + честная дистрибуция, измерение отклика; масштаб — только после сигналов.

## 5. Как это превращается в «автоматизировано из задач»

Промо моделируется как **домен** в существующем конвейере.

### 5.1 Структура (предлагаемая)

```
domains/growth/
  channel-registry.bvc        # площадки + capability tier (A/B/C) + наличие токена
  workitem-template.bvc       # шаблон промо-задачи
  evidence-contract.bvc       # что считать доказательством публикации
  workflows/
    publish-article.bvc       # сценарий: статья → нарезка → публикация по каналам
    announce-release.bvc      # релиз npm/GitHub → анонсы
```

### 5.2 Шаблон промо-задачи (work item)

Поля, которые делают задачу машинно-исполнимой:
- `goal`: что продвигаем (фича/релиз/кейс) и для какой аудитории (RU 1С / EN dev).
- `channel`: целевая площадка + tier (A/B/C).
- `inputs`: исходник (AN-разбор, release notes, фича).
- `checks`: канонический URL проставлен; теги; нет спам-паттернов; язык соответствует аудитории.
- `evidence`: `published_url`, `platform`, `published_at`, снимок метрик (через API).
- `approval`: для tier B/C — `requires_human_confirm: true`.

### 5.3 Конвейер (полностью прослеживаемый)

```
AN-разбор (тема промо)
   → epic «Промо релиза X»
      → задачи по каналам (написать → нарезать → опубликовать → измерить)
         → agent worker исполняет (генерация + API-публикация tier A; черновик+approval tier B/C)
            → evidence: published_url + метрики
               → closing-анализ эпика (что сработало по каналам)
```

### 5.4 Триггеры автоматизации (Cursor Automations)

- **Релиз → анонс:** триггер `git` (PR merged / tag) → агент генерит release notes + посты → публикует tier A, ставит в approval tier B.
- **Регулярный контент:** `cron` (например, раз в неделю) → создать промо-задачу из бэклога тем → черновик статьи → approval.
- **Мониторинг:** `cron` (раз в день) → собрать метрики опубликованного через API → дайджест.
- **Headless-пакет:** через Cursor SDK в CI — массовая генерация submission-kit под все каналы.

## 6. Что нужно построить (минимальный каркас)

1. **`channel-registry`** с tier и наличием токена (что можно авто-A, что только draft-C).
2. **Адаптеры публикации** для tier-A каналов с официальным API (GitHub, npm, Dev.to, Hashnode, Telegram, Mastodon) — по образцу `onebaseRestEvidenceAdapter`: вызов → запись `evidence-record.v1` с `published_url`.
3. **Approval-gate** в worker loop: задачи tier B/C не публикуются без человеческого подтверждения (расширение `workItemExecutionGate`).
4. **Секреты:** токены в env (`GITHUB_TOKEN`, `DEVTO_API_KEY`, `TELEGRAM_BOT_TOKEN`, …), вне репозитория; адаптер без токена → статус `blocked` (как OneBase без Go).
5. **Метрики-коллектор:** опрос API площадок → снимок в evidence для closing-анализа.
6. **Anti-spam guard:** lint промо-задач (рейт-лимиты, запрет масс-комментинга, проверка «не накрутка»).

## 7. Дорожная карта (по приоритету и риску)

| Этап | Что | Tier | Зависимость |
|---|---|---|---|
| 1 | Контент-фабрика: статьи/посты/ассеты/локализация из AN-разборов | A | есть всё |
| 2 | Авто-каналы на своих API: GitHub release, npm, Telegram | A | токены |
| 3 | Dev.to + Hashnode + Mastodon адаптеры + approval-gate | B | токены, gate |
| 4 | Метрики-коллектор + еженедельный дайджест + closing-анализ | A | API чтения |
| 5 | Cursor Automations: релиз→анонс, weekly content, daily metrics | A/B | этапы 1–4 |
| 6 | Draft-pipeline для Habr/HN/Reddit/Product Hunt (человек публикует) | C | — |

## 8. Чего НЕ делать

- ❌ Авто-регистрация аккаунтов и обход CAPTCHA/верификации.
- ❌ Массовые комментарии/ответы/DM от имени бота.
- ❌ Накрутка звёзд/апвотов/отзывов, астротурфинг, фейковые личины.
- ❌ Публикация в каналы без официального API через браузерную автоматизацию (баны).
- ❌ Полная авто-публикация под брендом без approval, пока канал не доказан.
- ❌ Промо-спам непровалидированного продукта (см. AN-73): сначала ценность и пользователь.

## 9. Вердикт

«Автоматизировать продвижение из задач» — **реально и полезно, но в правильных границах**. ИИ закрывает уровень A почти полностью (производство и доставка контента, публикация через официальные API на своих токенах, сбор метрик) и помогает на уровне B (черновик + подтверждение). Уровень C — регистрация, комментинг, накрутка — **не автоматизируется**: это либо технически заблокировано, либо запрещено ToS, либо вредит бренду.

Практический первый шаг — не «армия ботов», а **контент-фабрика + 2–3 авто-канала на официальных API + approval-gate**, встроенные в существующий конвейер `AN → epic → задачи → evidence → closing`. Это даёт автоматизацию без репутационного риска и с полной прослеживаемостью каждой публикации.

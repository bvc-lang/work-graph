# AN-45: Разделы Work Graph — путеводитель по боковому меню

**Запрос:** «Сделай разбор по разделам сайдбара: Аналитика, Задачи, Доска, Проверки, Память, Архитектура, Промпты — что это, для чего, какая боль, цель, интерфейс, процесс, что происходит внутри; сравни с конкурентами; без англоязычного жаргона».

**Связи:** [AN-22](pipeline-analysis-to-board.md) (канон потока), [AN-44](competitor-analysis-vs-work-graph.md) (позиционирование), [AN-20](ux-current-state-and-vector.md) (интерфейс в целом).

---

## Кратко

Боковое меню Work Graph — это не «набор вкладок ради вкладок», а **маршрут работы с умным агентом**: сначала понять и зафиксировать смысл, потом разложить на задачи, взять в работу, проверить, запомнить. Основная цепочка — **Аналитика → Задачи → Доска → Проверки → Память**. Ниже разделитель — **Архитектура** и **Промпты**: вспомогательные инструменты, а не ежедневный поток.

Конкуренты (Linear, Jira, Cursor, Notion, Claude Note) закрывают **отдельные куски** — список задач, чат, память сессии, доска. Work Graph собирает **одну нить от вопроса до доказательства готовности** в одном репозитории, без облачной подписки на «ещё один трекер».

---

## Как разделы связаны между собой

Представьте конвейер смысла:

```
Аналитика  →  Задачи  →  Доска  →  Проверки  →  Память
  (зачем?)    (что?)     (кто и когда?)  (доказано?)  (что запомнили?)
```

**Архитектура** и **Промпты** стоят сбоку: первая показывает «карту системы», вторые — «правила для агента». Ими пользуются, когда нужно понять контекст или настроить поведение, но они не заменяют основной поток.

## Аналитика

### Что это

Журнал **разборов** — текстовых документов с номерами AN-1, AN-2, … В каждом: вопрос, аргументация, выводы, иногда связь с эпиками и задачами. Две подвкладки: **входящие разборы** (новые идеи, исследования) и **итоги закрытия** (что выяснили после завершения крупного блока работ).

### Для чего

Чтобы **мысль не жила только в чате с агентом**. Чат исчезает после сессии; разбор остаётся в репозитории, его можно найти, процитировать, превратить в задачи.

### Какую боль решает

- «Мы уже обсуждали это три недели назад — никто не помнит почему так решили».
- «Агент предложил план, но он нигде не зафиксирован как решение команды».
- «Куча заметок в Notion/Confluence, но нет связи с конкретными задачами в коде».

### Цель раздела

Быть **входной точкой канона**: отсюда рождаются эпики и атомы задач, сюда же возвращается **обратный разбор** после закрытия эпика.

### Как выглядит интерфейс

Список карточек (новые сверху), поиск, пагинация. Клик открывает **боковую панель деталей** с полным текстом, тегами, связанными файлами, иногда — вариантами решения и задачами, выведенными из разбора. Есть кнопка «Скопировать текст разбора» для передачи в другой инструмент.

### Процесс (типичный сценарий)

1. Возник вопрос («стоит ли делать X?», «как устроены конкуренты?»).
2. Агент или человек пишет документ в `work/analytics/`, строка попадает в журнал.
3. Оператор читает разбор в интерфейсе.
4. Если нужно действие — из разбора создаются задачи (вручную, скриптом или через подключение агента к репозиторию).
5. После закрытия эпика — пишется **итоговый разбор** (вторая подвкладка).

### Что происходит внутри (простыми словами)

Интерфейс читает **журнал записей** и подтягивает **текст из файлов** на диске. Никакого отдельного облачного сервиса: всё лежит в git рядом с кодом. Запись знает свой номер, тему, автора, дату, список связанных файлов.

### Сравнение с конкурентами

| Кто | Что похоже | Чего не хватает |
|-----|------------|-----------------|
| **Notion / Confluence** | база статей и решений | нет связи «разбор → задача → доказательство в коде» |
| **Linear / Jira** | описание в тикете | тикет не живёт как отдельный «аналитический слой» до появления задачи |
| **Cursor / Claude Note** | память сессии, заметки | мягкая память чата, не жёсткий журнал решений с номерами |
| **GitHub Discussions** | обсуждения | нет канона «AN → эпик → атом задачи» |

**Вывод:** конкуренты хранят **текст или задачи**, но не **цепочку «разбор как источник обязательств»**.

## Задачи

### Что это

Рабочая очередь **атомов задач** — единиц работы с идентификатором, заголовком, статусом, владельцем, зависимостями. Две подвкладки: **Бэклог** (ещё не готовы к исполнению) и **Архив** (завершённые). Задачи группируются по **эпикам** — крупным блокам, внутри которых лежат подзадачи.

### Для чего

Чтобы **разложить намерение на конкретные шаги** с владельцем, приоритетом и проверками — до того, как кто-то «просто начнёт кодить в чате».

### Какую боль решает

- «В чате агент завёл свой список дел — он не совпадает с тем, что в репозитории».
- «Не видно, какая подзадача к какому эпику относится».
- «Задача перешла в работу без анализа — потом выясняется, что делать её не нужно было».

### Цель раздела

Держать **единственный официальный бэклог** проекта: всё отслеживаемое — только здесь, в файлах формата «атом задачи» внутри репозитория.

### Как выглядит интерфейс

Длинный список строк с заголовком, статусом, эпиком-сверткой (можно развернуть/свернуть). Фильтры: цикл, домен намерения, текстовый и смысловой поиск. Клик — **боковая панель** с полным атомом: базис, вектор, цель, блоки «Анализ» и «Решение», свидетельства, зависимости, связь с разбором.

### Процесс

1. Из разбора или напрямую создаётся эпик и подзадачи (статус обычно «бэклог»).
2. Заполняется блок **Анализ** («стоит ли делать?»).
3. Принимается **Решение** (полезно / отложить / вредно).
4. После закрытия зависимостей задача переводится в «готов к работе».
5. Дальше — на **Доску** для захвата и исполнения.

### Что происходит внутри

Каждая задача — **текстовый файл-атом** в дереве намерений проекта. Интерфейс собирает их в один список, считает прогресс эпиков, проверяет иерархию (родитель–ребёнок). Агент через подключение к репозиторию может создавать и обновлять те же файлы — поэтому бэклог один на всех.

### Сравнение с конкурентами

| Кто | Что похоже | Чего не хватает |
|-----|------------|-----------------|
| **Linear / Jira** | списки, эпики, подзадачи | нет обязательных блоков «анализ/решение» и атома смысла в git |
| **GitHub Issues** | задачи у кода | слабая модель намерения, нет этапа «решили не делать» |
| **Cursor plan mode** | план в чате | план не является источником правды в репозитории |
| **Todo в чате агента** | быстрый чеклист | параллельный бэклог, ломает учёт |

**Вывод:** трекеры решают **«кто что делает»**, но не **«почему это вообще в бэклоге и кто это решил»**.

## Доска

### Что это

**Исполнительный вид**: две доски одновременно — **канбан по стадиям планирования** (бэклог → готов → в работе → …) и **операционная доска** (готов к захвату, захвачен, выполняется, на проверке). Это место, где видно «что прямо сейчас движется».

### Для чего

Чтобы **перейти от плана к действию**: кто берёт задачу, что в очереди, что заблокировано. Здесь же видны подсказки «можно перевести в готов» для задач, прошедших подготовку.

### Какую боль решает

- «В бэклоге 200 задач — непонятно, что делать сегодня».
- «Агент взял задачу, но в интерфейсе это не отражено».
- «Нет единой картины статусов для человека и для агента».

### Цель раздела

Сделать **исполнение видимым**: захват задачи, работа, переход на проверку — всё на одном экране, синхронно с файлами в git.

### Как выглядит интерфейс

Колонки с карточками задач (как в классическом канбане). Фильтры цикла и домена — те же, что у «Задач». Клик по карточке — та же боковая панель с деталями, хронологией свидетельств, возможностью запустить агента (док-панель справа).

### Процесс

1. Задача в статусе «готов» появляется в колонке готовых.
2. Исполнитель (человек или агент) **захватывает** — статус «в работе».
3. По ходу работы добавляются **свидетельства** (что сделано, какие файлы, результат проверки).
4. Задача уходит в «на проверке» или «готово» — дальше роль **Проверок** и **Памяти**.

### Что происходит внутри

Интерфейс строит **проекцию колонок** из текущих статусов всех атомов. Изменение статуса через агента или вручную **перезаписывает тот же файл задачи** в репозитории — доска не отдельная база, а «окно» на те же данные.

### Сравнение с конкурентами

| Кто | Что похоже | Чего не хватает |
|-----|------------|-----------------|
| **Trello / Linear board** | колонки и карточки | карточка — не атом смысла с анализом и обязательными свидетельствами |
| **GitHub Projects** | доска у репозитория | нет захвата агентом и политики «готово только с доказательством» |
| **Devin / Cursor** | агент сам двигает работу | нет локального git-канона, всё в облаке исполнения |
| **PromptPilot** | очередь промптов | это «когда отправить запрос», а не «что считается сделанной работой» |

**Вывод:** доски конкурентов показывают **движение карточек**, Work Graph — **движение обязательств со следом**.

## Проверки

### Что это

**Пульт качества и автоматики**: матрица команд проверки (тесты, линтеры, опциональные интеграции), статус **генерации кода**, журнал фонового **демона**, последние **свидетельства** и **запуски воркера**, блок **пробелов в коде** (где код есть, а связи с задачей нет — предложения завести задачу).

### Для чего

Ответить на вопрос: **«можно ли считать работу доказанной?»** — не на словах агента, а по фактам: прогнались ли тесты, есть ли свидетельство, не сломан ли фоновый цикл.

### Какую боль решает

- «Агент сказал “готово”, но тесты не запускал».
- «Не видно, какие проверки обязательны, а какие по желанию».
- «Фоновый процесс упал — узнали случайно через час».
- «В коде появился модуль без привязки к задаче».

### Цель раздела

Быть **формальным контуром проверки готовности** — мост между «сделал в редакторе» и «репозиторий в согласованном состоянии».

### Как выглядит интерфейс

Несколько блоков-other на одной странице: таблица проверок с уровнями (обязательные / по окружению / с участием модели), списки недавних свидетельств и запусков, журнал событий демона, карточки **пробелов** с кнопкой «предложить задачу из пробела». Тяжёлый, «инженерный» экран — не для ежедневного планирования, а для контроля.

### Процесс

1. Задача на доске переходит в стадию проверки или завершения.
2. Исполнитель (или агент) добавляет свидетельство и запускает/ожидает **автоматические проверки**.
3. Оператор смотрит матрицу: что зелёное, что красное.
4. При пробелах в коде — из раздела можно **инициировать новую задачу** с черновиком.
5. Только после этого задача считается по-настоящему закрытой — и попадает в **Память**.

### Что происходит внутри

Страница собирает **сводку с сервера**: результаты заранее описанных команд, хвост журнала демона, данные отчёта о пробелах в коде, записи о последних запусках **живого цикла агента**. Это не «ещё одна доска», а **дашборд доверия к репозиторию**.

### Сравнение с конкурентами

| Кто | Что похоже | Чего не хватает |
|-----|------------|-----------------|
| **CI/CD (GitHub Actions и т.п.)** | автоматические тесты | не связано с конкретным атом задачи и разбором «зачем» |
| **Cursor** | агент сам гоняет тесты | нет единой матрицы «что обязано быть зелёным для этого проекта» |
| **SonarQube / линтеры** | качество кода | не знают про учёт работ и свидетельства в задаче |
| **Linear** | статус “Done” | галочка без доказательства |

**Вывод:** инструменты проверяют **код или пайплайн**, Work Graph проверяет **задачу как обязательство с доказательством**.

## Память

### Что это

**Долговременная память проекта** после завершённых работ: решения, инварианты, факты — с привязкой к задаче-источнику, файлам, уровню уверенности и пометкой «нужен ли пересмотр».

### Для чего

Чтобы **следующий агент или человек не начинал с нуля** и не повторял отвергнутые идеи. Память — не чат, а **отобранные следы** из закрытых задач.

### Какую боль решает

- «Claude Note / Cursor запомнили сессию, но это смешано с черновиками».
- «Confluence устарел, никто не знает, что ещё актуально».
- «Агент снова предлагает то, что мы уже отклонили в прошлом эпике».

### Цель раздела

Закрыть контур **«сделали → зафиксировали знание»** — финальная стадия канона после проверок.

### Как выглядит интерфейс

Список записей памяти: тип, статус, краткое содержание, откуда взялось (какая задача), связанные файлы. Поиск, в том числе по идентификатору задачи. Клик — боковая панель с деталями.

### Процесс

1. Задача проходит путь до «готово» с свидетельствами.
2. Система **формирует или дополняет** запись памяти (часть автоматически, часть из журнала).
3. Оператор просматривает, при необходимости помечает «нужен пересмотр».
4. При новой работе агент **подтягивает** релевантные записи через подключение к репозиторию (не через облачную память чата).

### Что происходит внутри

Записи собираются из **завершённых задач** и **журнала памяти** на диске. Это производная от учёта работ, а не отдельный блокнот.

### Сравнение с конкурентами

| Кто | Что похоже | Чего не хватает |
|-----|------------|-----------------|
| **Mem0 / Cursor Memories** | факты для агента | нет связи «память только из закрытой задачи с доказательством» |
| **Claude Note / Obsidian** | заметки и граф | нет статуса «обязательное знание проекта» vs «черновик чата» |
| **Confluence** | база знаний | ручное ведение, разрыв с задачами |
| **Letta / Zep** | долгая память агента | про «что агент помнит», не про «что команда приняла» |

**Вывод:** конкуренты решают **забывание в сессии**, Work Graph — **накопление решений после доказанной работы**.

## Архитектура

*(раздел ниже основной цепочки — вспомогательный)*

### Что это

**Карта крупных блоков системы** (уровень L1): какие подсистемы есть в проекте, как они связаны. Список блоков; клик открывает детали блока и связанные задачи.

### Для чего

Дать **ориентацию в большом репозитории**: «где мы меняем код, когда трогаем этот кусок продукта». Не заменяет задачи, но помогает не потеряться.

### Какую боль решает

- «300 задач и 40 папок — не вижу лес за деревьями».
- «Новый участник не понимает, из чего состоит система».

### Цель раздела

Связать **учёт работ** с **картой системы** — подсветка задач при выборе блока, переход из деталей задачи к блоку.

### Как выглядит интерфейс

Подвкладки (список блоков; раньше здесь же были графические виды — часть вынесена или упрощена). Список названий блоков, счётчик, бейдж «канон из устава» если есть.

### Процесс

Используется **эпизодически**: при планировании эпика, при онбординге, при разборе «куда класть новую фичу». В ежедневном потоке «аналитика → доска» не обязателен.

### Что происходит внутри

Блоки берутся из **устава и снимка архитектуры**, собранного из задач и структуры репозитория — не рисуются вручную в отдельном редакторе.

### Сравнение с конкурентами

| Кто | Что похоже | Чего не хватает |
|-----|------------|-----------------|
| **Backstage / C4-диаграммы** | каталог систем | нет живой связи с текущими задачами и статусами |
| **Sourcegraph** | карта кода | не про учёт работ и намерений |
| **Miro / FigJam** | схемы на стене | устаревают, не в git |

**Вывод:** карты конкурентов **описывают систему**, Work Graph **связывает карту с активными задачами**.

## Промпты

*(раздел ниже основной цепочки — вспомогательный)*

### Что это

**Библиотека правил поведения агента** — файлы с инструкциями «как работать в этом репозитории»: единый бэклог, как создавать задачи, как писать анализ, политика правок через подключение к репозиторию. Список с пометкой «валидно / есть ошибки».

### Для чего

Чтобы **агент в Cursor (или другом клиенте) не импровизировал** там, где нужен канон: не заводил параллельные списки дел в чате, не писал задачи без анализа.

### Какую боль решает

- «В правилах написано одно, а агент делает другое» — здесь видно, **какие правила вообще зарегистрированы**.
- «Промпт живёт в голове оператора» — правила версионируются в git.

### Цель раздела

Быть **витриной политик агента**, синхронной с тем, что лежит в папке правил репозитория.

### Как выглядит интерфейс

Список правил: имя, путь к файлу, статус проверки, превью текста. Редактор в боковой панели для просмотра содержимого.

### Процесс

1. Команда меняет правило в репозитории (или через интерфейс, если подключено).
2. Оператор сверяет список в разделе «Промпты».
3. Агент при старте сессии получает те же правила через клиент (Cursor rules + подключение к репозиторию).

### Что происходит внутри

Интерфейс **сканирует ограниченный набор файлов правил**, проверяет их формат и показывает сводку. Это зеркало диска, не облачный «магазин промптов».

### Сравнение с конкурентами

| Кто | Что похоже | Чего не хватает |
|-----|------------|-----------------|
| **Cursor Rules / CLAUDE.md** | инструкции в проекте | нет связи с бэклогом и проверкой «задача создана по канону» |
| **PromptLayer / LangSmith** | версии промптов | облако, не git-канон задач |
| **1C AI Dev Kit** | набор skills для 1С | только кодинг, не учёт работ |

**Вывод:** у конкурентов правила **настраивают агента**, у Work Graph правила **привязаны к единому учёту работ**.

## Общий вывод: чего не даёт рынок вместе

Если собрать типичный стек «Cursor + Linear + CI + Notion + Claude Note», получится:

- чат и код — в редакторе;
- задачи — в Linear;
- проверки — в CI;
- статьи — в Notion;
- память сессии — в заметках.

**Ни одно звено не отвечает на вопрос целиком:** «от разбора AN-7 до доказательства в git и записи в памяти — одна цепочка, один идентификатор задачи, без облачного трекера».

Work Graph в интерфейсе как раз и пытается показать эту цепочку **слева направо в меню**. Слабое место сегодня — **удобство** (много списков, боковая панель вместо разделённого экрана, нет палитры быстрых команд как в Linear). Сильное — **полнота контура**, если оператор уже принял канон.

## Рекомендации (для продукта)

| ID | Смысл |
|----|--------|
| **R1** | Считать основной поток только пятью разделами; Архитектура и Промпты не смешивать с ежедневным «что делать». |
| **R2** | Для внешнего пользователя продавать не «ещё одну доску», а **подключение агента к репозиторию** + этот интерфейс как пульт. |
| **R3** | Улучшать связи: из разбора — в задачи, из задачи — в проверки и память одним кликом (частично уже есть в боковой панели). |

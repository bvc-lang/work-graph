# AN-75: Parent vs Depends On — guardrails для эпиков и подзадач

**Запрос:** как решить проблему, когда задачи были связаны с эпиком через `work.depends_on`, но не отображались как подзадачи, потому что UI использует `work.parent_id`.

## Краткий вывод

Нужно зафиксировать в продукте два разных смысла:

- `work.parent_id` — **вложенность**: подзадачи, группировка в UI, rollup эпика.
- `work.depends_on` — **порядок исполнения**: что блокирует старт задачи.

Ошибка возникла потому, что зависимости были использованы как иерархия. UI сделал всё правильно: он показывает children только по `work.parent_id`.

## Что нужно сделать

1. **Линтер.** Если задача зависит от эпика (`work.depends_on: epic-*`), но не имеет `work.parent_id`, выдавать warning/error: скорее всего, забыли привязать подзадачу.
2. **Создание задач.** В `create_work_item` / batch-flow добавить явный `parentId`; для `itemKind=subtask` он должен быть обязательным.
3. **UI-подсказка.** Если эпик без children, но есть задачи с `depends_on` на него, показывать подсказку «найдены зависимые задачи без parent_id».
4. **Документация шаблона.** В правилах создания эпиков указать: для подзадач всегда ставить `work.parent_id`, а `work.depends_on` использовать только для порядка.

## Пользовательский смысл

Оператор не должен помнить внутреннюю разницу между зависимостью и вложенностью. Если система видит вероятную ошибку моделирования, она должна подсветить её сразу и предложить исправление.

## Вердикт

Минимальный правильный MVP: **lint rule + тест + create_work_item guard**. UI-подсказку можно сделать вторым шагом, но она полезна для обнаружения уже существующих ошибок в бэклоге.

# AN-44: Аналитика конкурентов vs Work Graph (рынок 2026)

**Запрос:** «сделай аналитику конкурентов и сравни их с WG, запиши в разбор».

**Дата:** 2026-06-01. Источники — публичные обзоры рынка AI-разработки и слоёв памяти для ИИ за апрель-май 2026 + экосистема 1С/Infostart (см. §8). Развивает [AN-7](product-self-audit-user.md) (позиция C) и [AN-31](promptpilot-claude-note-vs-work-graph.md).

---

## Кратко

- **Прямых конкурентов у WG нет.** Рынок 2026 — это **горизонтальные** AI-агенты (Cursor, Claude Code, Windsurf, Devin) и **слои памяти** (Mem0, Letta, Zep). Ни один не делает **бэклог на доказательствах с `work.id` + трассировкой + проверкой готовности**, и почти никто не идёт в **вертикаль 1С/OneBase**.
- **WG — не агент и не IDE.** WG — это **слой «источника правды о работе»**: `AN → эпик → .work.bvc → claim → evidence → verification → memory` (разбор → эпик → атом работы → захват → доказательства → проверка → память). Конкуренты живут на слоях *исполнения* и *памяти сессии*, а не *учёта работ и доказательств*.
- **Реальное поле боя WG — вертикаль 1С** (позиция C из AN-7). Там конкуренты — **MCP-мосты к 1С** (`mcp-1c`, `onec-mcp-universal`, `bsl-context`) и **1C AI Dev Kit**. Они решают *анти-галлюцинацию* (метаданные/синтаксис), но **не управление работой и не доказательства готовности**. Это комплемент, а не замена.
- **Главная угроза — не конкурент, а коммодитизация:** `Cursor (Memories + Background Agents + Automations + MCP)` уже покрывает ~70% обещаний WG, и пользователь уже там. Окно WG — там, где Cursor *структурно не пойдёт*: жёсткий канон смысла, локальность/git, аудит AI-кода и узкая 1С-вертикаль.

## 1. Что именно сравниваем (позиция WG)

Из `README.md` и [AN-7](product-self-audit-user.md): WG = «разработка с LLM не чатом, а **обходимым графом задач со следом**», ставка — **позиция C: вертикаль для 1С/OneBase**.

Слой WG в стеке AI-разработки:

```
[ Память сессии ]      [ Исполнение ]            [ ИСТОЧНИК ПРАВДЫ — WG ]      [ Продуктовый runtime ]
mem0 / Letta / CN  →   Cursor / Claude Code  →   AN→epic→.work.bvc→evidence  →  OneBase / ioHasC
```

Поэтому конкурентов делим на **4 сегмента по слою**, а не валим в одну таблицу.

Оси сравнения (общие для всех таблиц):

| Ось | Что меряем |
|---|---|
| **Слой** | память / исполнение / учёт работ / runtime |
| **Единица** | сообщение, задание, файл, PR, **`work.id`** |
| **Доказательства/проверка** | есть ли формальные свидетельства + проверка готовности |
| **Трассировка смысла** | связь намерение→решение→код→проверка |
| **Локальность** | local/git vs облако SaaS |
| **Вертикаль 1С** | есть ли понимание метаданных/BSL/OneBase |
| **Автономность** | насколько работает без человека |

## 2. Сегмент A — горизонтальные AI-агенты для кодинга (главные «отъедатели» аудитории)

Рынок 2026: Cursor (~2M польз., $2B ARR, Composer 2, до 8 параллельных агентов, **Memories**, **Background Agents**, **Automations**, MCP), Claude Code (терминал, SWE-bench **80.8%**, skills/hooks/subagents/память проекта, контекст 1M), Windsurf (Cascade, модель SWE-1.5, **codemaps**, куплен Cognition), Devin (автономная VM, ACU-биллинг, сам открывает PR), Copilot (~26M польз., Workspace plan→PR), Aider (CLI с открытым исходным кодом, несколько моделей).

| Инструмент | Слой | Единица | Доказательства/проверка | Трассировка смысла | Локальность | 1С |
|---|---|---|---|---|---|---|
| **Cursor** | исполнение (IDE) | файл/диф/PR | тесты, нет формальной проверки готовности | `.cursor/rules` + Memories (мягко) | облако (LLM) | нет |
| **Claude Code** | исполнение (CLI) | файл/коммит/PR | прогон тестов, автокоммит | память проекта / CLAUDE.md | облако (LLM) | нет |
| **Windsurf** | исполнение (IDE) | файл/диф | тесты, codemaps | flow-context | облако/частично локальные модели | нет |
| **Devin** | автономный инженер | тикет→PR | сам тестит/ревьюит, нет аудита канона | планы в VM | облако (VM) | нет |
| **Copilot** | расширение | автокомплит/PR | Workspace plan | слабо | облако (GitHub) | нет |
| **Aider** | CLI | диф/коммит | git-диф | нет | локальный режим + API | нет |
| **WG** | **учёт работ** | **`work.id`** | **хронология доказательств + lint + проверка готовности** | **AN→эпик→bvc→trace** | **полностью local/git** | **да (OneBase)** |

**Вывод по A:** это **не конкуренты по функции** — они пишут код, WG ведёт *учёт работ и доказательства*. Но они **конкуренты за внимание и кошелёк**: пользователь уже сидит в Cursor/Claude Code. WG проигрывает им по UX, скорости, экосистеме, маркетингу (это прямо зафиксировано в AN-7 §7) и **не должен** пытаться их догонять (анти-цели в README). Правильная стратегия — **встроиться MCP-слоем поверх** них, а не заменять.

## 3. Сегмент B — слой задач/PM (куда WG похож по форме, но не по сути)

| Инструмент | Что делает | vs WG |
|---|---|---|
| **Linear** | лучший UX задач, скорость, интеграции, mobile | WG проигрывает по PM-UX, но Linear **не знает про код, доказательства, claim агента, канон** |
| **GitHub Projects / Issues** | задачи у кода, автоматизация | нет смыслового канона, нет проверки готовности, нет 1С |
| **Copilot Workspace** | plan → tasks → PR внутри GitHub | владеет GitHub; нет локальности, нет `.bvc`, нет 1С |
| **Jira** | корпоративный PM | тяжёлый, не для AI-цикла, нет доказательств по коду |

**Вывод по B:** Linear+агент собирается за день и закрывает «команда + процесс» лучше WG (AN-7 §7). Но **никто из B не связывает намерение→код→проверку как атом** и не работает локально в git. Дифференциатор WG здесь — **`.bvc`-канон + проверка на доказательствах**, а не «ещё одна доска».

## 4. Сегмент C — память / контекст (растущий слой, частично пересекается)

Рынок 2026: Mem0 (Apache-2.0, ~48K★, vector+graph, ADD/UPDATE/DELETE, managed+self-host), Letta/MemGPT (OS-метафора, агент сам пейджит память), Zep/Graphiti (**темпоральный граф знаний** — как факты меняются во времени), Cognee (KG для reasoning), плюс MCP-memory-серверы для Cursor/Claude (claude-mem, Context Cloud, memobase, Basic Memory). **Тренд 2026: журналы аудита по умолчанию (давление EU AI Act).**

| Инструмент | Что хранит | Структура | vs WG |
|---|---|---|---|
| **Mem0** | факты из диалога | плоский + entity-граф | нет состояния работ, нет «готово+доказательство» |
| **Letta** | рабочая/архивная память | OS-tiered | про память агента, не про учёт работ |
| **Zep/Graphiti** | темпоральный граф фактов | KG во времени | ближе всех по «эволюции знания», но не моделирует `done`+доказательства |
| **Cursor Memories / mem0 / claude-mem** | проектная память сессий | семантическое вспоминание | **встроены в рабочий процесс** — главный риск для WG |
| **Claude Note** ([AN-31](promptpilot-claude-note-vs-work-graph.md)) | выводы сессии → Obsidian/MEMORY.md | повествовательный Markdown | мягкая память; WG — жёсткий контур |
| **WG** | решения (AN), эпики, `.work.bvc`, closing | bvc + JSONL + lint + MCP | **«что обязаны сделать и доказать»**, не «что поняли» |

**Вывод по C:** слой памяти решает *забывание контекста*, WG решает *учёт обязательств и доказательств*. Пересечение — оба пишут «правила для агента» → риск **двойной памяти** (см. AN-31 §3.2). Интересный сигнал: тренд на **журналы аудита / темпоральный граф** идёт навстречу core-идее WG (доказательства + трассировка). WG может позиционироваться как **«аудит-след по умолчанию для AI-кода»**, пока вендоры памяти это только обещают.

## 5. Сегмент D — вертикаль 1С / OneBase (РЕАЛЬНОЕ поле боя WG)

Здесь живёт ставка C из AN-7. Конкуренты-2026 — это **MCP-мосты к 1С** и **наборы skills**, а не PM/системы доказательств:

| Инструмент | Что делает | Слой | vs WG |
|---|---|---|---|
| **mcp-1c** (nVoRoN) | дерево метаданных, структура объектов/форм, `execute_query`, `bsl_syntax_help` (180 функций) | domain MCP (анти-галлюцинация) | даёт агенту *контекст 1С*; **не ведёт работу и не доказывает готовность** |
| **onec-mcp-universal** (Seleznev) | единый шлюз, маршрутизация по сессиям, BSL LSP, docs платформы | шлюз domain MCP | инфраструктура контекста; нет `work.id`/доказательств/канона |
| **1c_mcp** (Kharin) | расширение 1С + Python-прокси, MCP внутри 1С | domain MCP (внутри платформы) | глубокая интеграция данных; не PM |
| **bsl-context / mcp-bsl-platform-context** | синтаксис/справка платформы | помощник проверки | это **проверочный контур** для WG, не бэклог |
| **1C AI Development Kit** | 50+ skills + правила + агенты для Claude Code/Cursor | пакет skills | ускоряет кодинг; нет учёта работ и трассировки |
| **PromptPilot** ([AN-31](promptpilot-claude-note-vs-work-graph.md)) | очередь промптов, расписание, Telegram | планировщик исполнения | когда/какой промпт; не что/готово/доказательство |
| **WG (вертикаль OneBase)** | `charter.bvc → .work.bvc → claim → trace/evidence → verify → memory` для документов/обработок/отчётов OneBase | **учёт работ + доказательства** | единственный, кто закрывает PM+доказательства для 1С-LLM-разработки |

**Вывод по D — ключевой:**
- В 1С-нише уже есть **сильный слой контекста** (MCP-метаданные + BSL-справка). Это значит: **WG не должен делать свой 1С-MCP с нуля** — он должен **потреблять** эти мосты как источники доказательств (`onebase` tools, bsl-context как проверочный контур — см. [AN-17](onebase-integration-vertical-stack.md)).
- В 1С-нише **никто не делает бэклог на доказательствах с трассировкой и проверкой готовности**. Это **белое пятно** и реальный дифференциатор WG.
- Эти инструменты — **комплемент**: их контекст + WG-учёт = полный цикл. Риск тот же, что в AN-31: **тройной бэклог** (PromptPilot jobs + chat TODO + WG), если не зафиксировать, что бэклог один — WG.

## 7. Где WG выигрывает / проигрывает / под угрозой

### Выигрывает (защитимо)
1. **Канон смысла `.bvc`** — структура намерения, которой нет ни у кого (потенциальный «Markdown 2.0 для разработки»).
2. **Бэклог на доказательствах + проверка готовности** — «доказательство готовности», а не «задача выполнена». Совпадает с трендом 2026 на журналы аудита (EU AI Act).
3. **Полная локальность / git** — приватность и локальная инсталляция из коробки; Cursor/Devin/Linear облачные.
4. **Вертикаль 1С/OneBase** — никто из крупных игроков туда не идёт; контекст-мосты уже есть, PM-слоя нет.

### Проигрывает (не догонять — анти-цели)
- UX, скорость, автокомплит, индексация, экосистема, маркетинг — Cursor/Windsurf/Claude Code (AN-7 §7).
- Автономность «тикет→PR» — Devin/OpenHands.
- PM-UX команд — Linear.

### Под угрозой (главное)
- **Коммодитизация Cursor:** `Memories + Background Agents + Automations + MCP` ≈ 70% обещаний WG, и пользователь уже там (AN-7 §7, подтверждено обзорами 2026).
- **Вендоры памяти** двигаются к темпоральному графу + журналам аудита — заходят на территорию «трассировка/доказательства» WG.
- **1С-MCP экосистема** быстро растёт (несколько активных серверов) — если кто-то из них добавит учёт работ, окно сузится.

## 8. Рекомендации (решения)

| ID | Решение |
|---|---|
| **D1** | **Не конкурировать на слое исполнения/IDE.** Держать анти-цели README. WG = MCP-слой «источник правды», подключаемый к Cursor/Claude Code. |
| **D2** | **1С-вертикаль = главный фронт.** Потреблять готовые 1С-MCP (`mcp-1c`/`onec-mcp-universal`) и bsl-context **как источники доказательств и проверки**, не строить свой с нуля (усиление [AN-17](onebase-integration-vertical-stack.md)). |
| **D3** | **Позиционировать как «аудит-след по умолчанию для AI-кода».** Это отстройка и от вендоров памяти, и от Cursor: они *обещают* аудит, WG делает его ядром (доказательства+проверка готовности+трассировка). |
| **D4** | **Один бэклог.** Жёстко держать границы против тройного бэклога (WG vs PromptPilot vs chat TODO) — см. [AN-25](agent-bypass-work-graph-dual-backlog.md), [AN-28](chat-work-graph-todo-sync.md), [AN-31](promptpilot-claude-note-vs-work-graph.md). |
| **D5** | **Метрика дифференциатора.** Демонстрировать на 1С эталонном пути то, чего нет у конкурентов: «задача → доказательства → проверка готовности», воспроизводимо не-автором (см. `docs/golden-path-pilot-runbook.md`). |

## 10. Кратко (повтор)

- WG не на одном слое с Cursor/Devin/mem0 — он про **что делать + доказательство**, а не про код, расписание или память.
- Прямых конкурентов нет; есть **отъедатели внимания** (горизонтальные агенты) и **комплементы** (1С-MCP, память, планировщик).
- Защитимое ядро: **`.bvc`-канон + доказательства/проверка готовности + локальность + 1С-вертикаль**.
- Главный риск — **коммодитизация Cursor**, ответ — уходить туда, куда Cursor структурно не пойдёт: жёсткий канон, аудит AI-кода, узкая 1С-вертикаль поверх готового контекста.

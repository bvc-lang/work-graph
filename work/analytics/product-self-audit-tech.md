# AN-6: Критический технический анализ Work Graph Rebuild

**Запрос:** «нужен критический анализ текущего продукта» (техническая сторона).

## Кратко

Продукт делает то, что заявил **в формате**, но нарушает то, что заявил **в анти-целях** (`charter/main.bvc`). Превратился в собственную IDE-оболочку с монолитным сервером на 6357 строк, обслуживающую свою же разработку. Внешней ценности (domain vertical OneBase) почти не видно — поток усилий уходит в backlog UI и визуализацию.

## Сильные стороны

1. **Чистый стек.** Node + `node:test` + esbuild + lit-flow + zod. Никаких vite/react/webpack. 7 prod-deps. Обновлять и понимать дёшево.
2. **Канон смысла в `.bvc`.** Один формат для устава, правил, задач, планов. 233 `.work.bvc` живут на диске и git, не в БД.
3. **AN-записки перед кодом.** AN-1…AN-5 фиксируют root-cause до правок. Реально помогли (AN-5 спасла от очередной правки bezier вслепую).
4. **На себе.** Бэклог ведётся через собственный Work Graph.
5. **104 теста** на чистых функциях + детерминированный CI gate (`ci:mandatory`) — быстро и стабильно.

## Критические проблемы

### 1. Монолит UI-сервера — главная угроза

`src/workGraphBacklogUiServer.mjs`: **6357 LOC / 249 KB, 40 if-роутов, HTML inline, 0 шаблонов.**

- Прямое нарушение анти-цели *«Не строить собственную IDE shell до доказательства рабочий процесс»* (`charter/main.bvc`).
- Каждая фича (drawer, граф, минимап, prompt editor, semantic search, kanban, evidence) добавляет в этот файл сотни строк.
- Нет роутера → 40-я ветка `if (pathname === ...)`. Поиск, замена и review деградируют квадратично.

### 2. «228 verified из 233» — статистический мираж

228 задач помечены `verified` за <30 дней. Многие созданы сегодня же `seed:*` скриптами и сразу пошли в verified. Метрика **обесценена**: значит «загружено сидом», а не «прошло эталонный сценарий с evidence».

```
verified: 228   pending: 4   backlog: 1
```

Гейт между статусами слаб или отсутствует. Charter обещал `trace.status: verified` как доказательство, на деле — административный лейбл.

### 3. Три layout-движка параллельно

- ручная сетка `POSITIONS` в `architectureLayout.mjs` / `schematicView.mjs`
- dagre + work-stack в `intentRoadmapCanvas.mjs`
- lit-flow + SVG-overlay (`graphCanvasSvgEdges.ts`)

AN-1 предлагал **единый** движок — вместо этого добавился ещё один слой.

### 4. Lit-flow используется на 30% и опасно

- узлы рисует lit-flow;
- рёбра — SVG поверх shadow DOM (хак через `viewport.insertBefore`);
- нативные `flow-edges-layer` погашены CSS `display:none`;
- MutationObserver следит, не убил ли lit-flow слой.

Любой минорный апдейт lit-flow ломает всё. Зависание браузера (фикс часом ранее) — следствие именно этого хака.

**Честные варианты:**
- (a) Полностью на lit-flow с custom edge component (PR или fork);
- (b) Уйти от lit-flow → свой canvas + dagre + SVG (как было до AN-4);
- (c) Заменить lit-flow на ReactFlow / Vue Flow.

Гибрид — худший вариант: оплачено всё, использовано мало.

### 5. Backlog раздут церемонией

Эпик из 5 задач на ~300 строк кода (SVG-фикс AN-5) — **больше метаданных, чем кода**. Каждый `.work.bvc` имеет basis/vector/goal/checks/targetFiles.

**Правило:** epic = ≥3 файла или ≥1 неделя. Тактика — один work item.

### 6. Charter vs. реальность

| Анти-цель из `charter/main.bvc` | Реальность |
|---|---|
| «не строить собственную IDE shell» | `workGraphBacklogUiServer.mjs` — IDE shell |
| «не переносить монолитный orchestrator» | `workGraphRuntime.mjs` (30 KB) + UI server = новый монолит |
| «MVP остаётся узким» | 126 src-файлов, 48 npm-скриптов, 8 plan-docs |
| «Markdown не канон» | AN-записки и plan-`.md` стали де-факто каноном решений |

Charter перестал служить компасом.

### 7. Нет внешней ценности

Эталонный сценарий `charter → workgraph → trace → verified` **описывает сам себя**: продукт нужен, чтобы вести разработку продукта. Заявленный OneBase/1C виден в `src/onebase*.mjs` как побочная линия — без UI-демо, без сценария «1С-разработчик решает свою задачу через Work Graph».

### 8. Тесты есть, UI нет

104 теста — все на чистых функциях / проекциях. Зависание браузера час назад никакой тест не поймал. Playwright E2E лежит, но не в `ci:mandatory`.

## Риски

| Риск | Вероятность | Удар |
|---|---|---|
| Bus factor = 1 | высокая | высокий |
| Lit-flow upgrade ломает SVG-хак | средняя | средний |
| UI-сервер дойдёт до 10 K LOC и станет нередактируемым | высокая | высокий |
| Verified inflation обесценит доверие к статусам | высокая | средний |
| 233 work items → проекции деградируют | средняя | средний |
| Charter перестанут читать | высокая | высокий |

## Рекомендуемый план на 1-2 недели

В порядке окупаемости:

1. **Декомпозировать `workGraphBacklogUiServer.mjs`** на `routes/`, `views/`, `api/`. Не переписывать — вынести по доменам (graph, backlog, evidence, prompts) с тонким маршрутизатором.
2. **Ввести evidence-gate перед `verified`.** Минимум: ссылка на тест / trace / commit. `lint:backlog` падает, если verified без evidence.
3. **Решить вопрос lit-flow** — выбрать (a/b/c) и зафиксировать в ADR.
4. **Обновить `charter/main.bvc`** под факт: либо признать IDE shell как часть MVP, либо вырезать половину UI-сервера.
5. **Один пользовательский сценарий на OneBase** — пройти эталонный сценарий задачей для 1С-разработчика, не для Work Graph.
6. **Сократить церемонию задач**: ввести `itemKind: 'task'` без подзадач для мелких фиксов.
7. **Добавить hang/perf E2E**: Playwright-тест на блокировка основного потока >500мс.

## Что не делать

- Не добавлять новых view'ев и панелей, пока UI-сервер не декомпозирован.
- Не запускать новые seed-скрипты.
- Не лезть в Genesis / GVM / Zig.
- Не оптимизировать edge router дальше, пока не решён вопрос lit-flow.

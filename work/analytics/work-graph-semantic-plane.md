# AN-68: Смысловая плоскость (Semantic Plane) WG — навигация по намерению

**Запрос:** можно ли с помощью WG и BVC строить смысловую плоскость и навигацию по ней?

**Дата:** 2026-06-04  
**Статус:** разбор (pre-epic)  
**Ключ журнала:** AN-68

**Связи:** [AN-65](work-graph-intent-information-plane.md) (информационная плоскость — структура и связи), [AN-3](intent-graph-storage-roadmap.md) (эволюция намерения question→decision→work), [AN-10](pvrg-verified-reference-graph.md), [AN-38](llm-pvrg-richir-memory-slices-usage-audit.md) (семантические срезы), [AN-50.1](work-graph-bvc-contract-verification.md) (BVC как контракт), [AN-40](work-graph-project-deployment-model.md) (пример в дрифте — deployment model).

**Примечание:** в черновике предлагался **AN-52** — ключ занят [closing epic BVC contract verification](closing-epic-work-graph-bvc-contract-verification-v1.md) (журнал `analytics-records.jsonl`).

**Отличие от AN-65:** информационная плоскость отвечает на *«как связаны файлы и задачи?»* (топология, evidence, статусы). Смысловая плоскость — на *«как меняется понимание проекта и где смысл размывается?»* (контекст, эволюция, alignment намерения и кода).

---

## Короткий ответ

**Да.** Это качественный скачок от **«где лежат файлы»** к **«что мы пытаемся сделать и почему»**.

В контексте Work Graph + BVC это реализуется через **физику намерения**: проект как пространство, где каждая задача — вектор силы, меняющий состояние системы.

---

## 1. Определение: что такое смысловая плоскость?

Динамическое пространство, где координатами являются не папки и статусы, а **смысловые векторы**.

| Элемент | Роль в модели | Пример в WG |
|---------|---------------|-------------|
| **Origin (точка отсчёта)** | Корневой смысл — «зачем мы здесь?» | `AN` (аналитический разбор) |
| **Vectors** | Направления изменений | `Epic`, `Work Item` — `Basis` + `Vector` в BVC |
| **Field** | Текущее состояние реализации | Состояние кодовой базы (`Codebase state`) |
| **Collisions** | Столкновение намерения с реальностью | `Evidence` — тест прошёл/упал, код принят/отклонён |

**Смысловая плоскость измеряет «расстояние» между задуманным (BVC) и получившимся (код + тесты).**

---

## 2. Навигация по смысловой плоскости

Навигация не по ID или дате, а по **смысловым запросам**.

| Тип навигации | Запрос (пример) | Что возвращает система |
|---------------|-----------------|------------------------|
| **Semantic Scope** | «Покажи всё, что касается платежного шлюза» | Задачи, код и `AN` с высоким семантическим весом «платежи», в т.ч. без точного слова (эмбеддинги BVC) |
| **Drift Detection** | «Где отклонились от плана `AN-40`?» | Задачи, где код далек от `Goal` в BVC или `Basis` устарел |
| **Trace of Meaning** | «Как менялось решение по авторизации?» | Цепочка: `AN (идея)` → `Epic (план)` → `Work (попытка 1, отклонена)` → `Work (попытка 2, успех)` |
| **Semantic Voids** | «О чём забыли в контексте безопасности?» | Области кода без смысловых связей (нет BVC-атомов, тестов, контекста) |

Существующий задел: `get_graph_rag_context`, смысловой поиск в UI ([AN-45](work-graph-sidebar-sections-guide.md)), PVRG scope — но не как единая **Semantic Plane**.

---

## 3. Как BVC делает это возможным

BVC — не просто текст, а **модель смысла** для измерения:

| Поле BVC | Роль в плоскости |
|----------|------------------|
| **Basis** | Система координат: контекст, ограничения, прошлые решения («гравитационное поле» задачи) |
| **Vector** | Направление и «модуль» изменения: что меняем и насколько глубоко |
| **Goal** | Точка притяжения, критерий истинности |

**Метрика смыслового выравнивания (концепт):**

```
Alignment = cosine_similarity( embed(BVC.Goal), embed(Code_Result) )
```

Низкий `Alignment` → **смысловой разрыв** (агент ошибся или задача сформулирована плохо). WG должен фиксировать это в evidence / gates, не только в субъективной ревью.

---

## 4. Техническая реализация (MCP-слой)

Инструменты, оперирующие **смыслами**, а не только путями к файлам.

### 4.1. `query_semantic_field({ q, scope, depth })`

| | |
|---|---|
| **Вход** | Текст или теги (`billing`, `latency`, `security`) |
| **Выход** | Граф сущностей (AN, Work, Code, Evidence), ранжированный по смысловой близости |
| **Для** | Контекст агента без кодинга «в вакууме» (режим 1 навигатора, §8) |

### 4.2. `detect_semantic_drift(work_id)`

| | |
|---|---|
| **Вход** | ID задачи |
| **Выход** | Скор дрифта `0.0`–`1.0`: `BVC.Goal` vs `git diff` + результаты тестов |
| **Для** | Автофлаг «риск: код не решает задачу» |

### 4.3. `resolve_semantic_conflict(work_id_A, work_id_B)`

| | |
|---|---|
| **Вход** | Две параллельные задачи |
| **Выход** | Анализ противоречий (напр. «строгая типизация» vs «any types») |
| **Для** | Предотвращение коллизий между параллельными агентами |

**Связь с AN-65:** `query_intent_plane` — обход **структуры**; semantic MCP — измерение **смысла** и дрифта поверх той же плоскости.

---

## 5. Зачем бизнесу и разработчику

1. **Анти-галлюцинация на уровне проекта** — код синтаксически верен, но смыслово неверен; сравнение вектора намерения с вектором реализации.
2. **Onboarding** — «карта смыслов» за секунды: финтех-зона, security-critical, legacy «не трогать».
3. **Долгосрочная память** — ответ на «почему этот код?» через намерения (BVC), не только grep по ключевым словам.

---

## 6. Границы (anti-goals)

| Не делать | Почему |
|-----------|--------|
| Подменять информационную плоскость | Смысл без топологии и evidence — галлюцинация карты |
| Строить «общую KB» проекта | Semantic plane — **рабочие намерения + проверка реализации**, не wiki |
| Доверять только эмбеддингам | Alignment — сигнал; истина — gates, тесты, human claim |
| Свободный semantic crawl для агента | Только в scope задачи + audit trail |

---

## 7. Рекомендуемая структура следующего артефакта

После принятия разбора — эпик + plan:

1. Формализация «семантического вектора» задачи (BVC → embedding / features)
2. Метрики дрифта (смысл vs код, пороги, evidence types)
3. Спецификация MCP навигатора (§8): `query_semantic_field`, `detect_semantic_drift`, `find_semantic_voids`, `get_context_slice`, `navigate_temporal_plane`, `resolve_semantic_conflict`
4. UI: не только граф связей (AN-65), а **тепловая карта намерений** (плотность смысла / выгорание)
5. Roadmap: P0 (drift + field map) → P1 (conflict + voids) → P2 (temporal trace of meaning)

## 8. Навигатор по смысловой карте: что он сможет делать

**Навигатор** — не поиск по тексту и не визуализация графа `depends_on`. Это запрос к *намерениям проекта*: отвечает на «почему?», «насколько близко?», «что потеряно?», а не только «где лежит файл?».

Реализуется поверх смысловой плоскости (§1–3) через MCP + UI-проекции. Существующий задел: `get_graph_rag_context`, `get_pvrg_task_scope` — предшественники режимов 1 и 4.

### 8.1. Пять режимов работы

| Режим | Что делает | MCP / UI | Пример запроса |
|-------|------------|----------|----------------|
| **1. Семантический поиск** | Контекстные срезы: BVC-атомы, код, evidence, семантически близкие запросу | `query_semantic_field({ q, scope, depth })` | «Всё про экспорт отчётов в 1С, включая отклонённые решения и тесты-гейты» |
| **2. Детекция дрейфа** | `BVC.Goal` vs `Code+Tests`; `drift_score` 0.0–1.0 | `detect_semantic_drift({ work_id \| scope })` | «Где код ушёл от намерения AN-42? Задачи с drift > 0.6» |
| **3. Поиск вакуумов** | Смысловые дыры: код без намерения (легаси-зомби), намерения без кода (висящие AN) | `find_semantic_voids({ domain, tier })` | «Код в `src/payments` без задачи и без evidence» |
| **4. Контекстная маршрутизация** | Для агента: не весь репо, а релевантный пакет (BVC, прошлые ошибки, allowlist) | `get_context_slice({ work_id, agent_role })` | «Что знать, чтобы править валидатор?» → contracts + past failures |
| **5. Временная навигация** | Как менялся смысл: срез плоскости на дату, diff кластеров | `navigate_temporal_plane({ date, scope })` | «Карта смыслов 1 марта vs сегодня — новые и исчезнувшие кластеры» |

Дополнительно (параллельные агенты): `resolve_semantic_conflict(work_id_A, work_id_B)` — см. §4.3.

**MCP resource (опционально):** `workgraph://semantic/{scope}` — read-only снимок поля для IDE/агента без полного tool round-trip.

### 8.2. Сценарии: человек (архитектор / техлид)

| Сценарий | Поведение навигатора |
|----------|----------------------|
| **«Почему мы так решили?»** | Клик на узел карты → цепочка `AN → Epic → Work → Evidence → Decision` (воспроизводимый след, не гадание) |
| **«Что сломается, если поменять это?»** | Impact по **смысловым** связям: зависимые контракты и гейты, не только import-граф |
| **«Где смысл-долг?»** | Heatmap дрейфа: зоны, где код давно не синхронизирован с BVC-намерениями (`detect_semantic_drift` по scope) |

### 8.3. Сценарии: агент (Cursor / Claude Code / OpenCode)

| Сценарий | Поведение навигатора |
|----------|----------------------|
| **Контекст без шума** | `get_context_slice` → 3–5 релевантных BVC + evidence + запрещённые паттерны; промпт не переполняется |
| **Самопроверка перед коммитом** | `detect_semantic_drift` в pre-commit / verify hook; при `drift_score > threshold` → `violations[]`, правка до `assert_ready` |
| **Навигация без блуждания** | `query_semantic_field` → ограниченный граф → работа только внутри scope задачи; контракт не нарушается |

Связь с [AN-57](agent-session-warmup-vs-enforcement.md): навигатор поставляет срез, enforcement удерживает `allowed scope`.

### 8.4. Под капотом (кратко)

| Компонент | Роль |
|-----------|------|
| **Векторизация BVC** | `Basis`, `Vector`, `Goal` эмбеддятся отдельно — различать контекст, действие, критерий |
| **Индекс кода + evidence** | Lightweight embeddings dev-контекста (специализированные code/test-модели, не тяжёлый general LLM на каждый запрос) |
| **Граф связей** | Precomputed adjacency: `work ↔ files ↔ evidence ↔ AN` + семантические рёбра (cosine similarity) |
| **MCP-слой** | Инструменты §8.1 + resource `workgraph://semantic/{scope}` |
| **Runtime** | Инкрементальное обновление индекса на `bvc:lint` + `verify`; UI читает снимки, не парсит git на лету |

### 8.5. Границы навигатора (не делает)

| Не делает | Почему |
|-----------|--------|
| Не заменяет `git grep` / IDE-поиск | Инструмент *смысла*, не точного совпадения строк |
| Не генерирует код | Только контекст и проверка дрейфа; codegen — IDE/агент |
| Не требует 100% NLP-точности | Fallback: контрактные поля BVC + точные совпадения; эмбеддинги — сигнал |
| Не хранит личные чаты / заметки | Только артефакты WG: BVC, evidence, code refs, verification logs |
| Не строит глобальный граф across repos | Один репо = одна плоскость; federation — P2 (как в AN-65) |

### 8.6. Сдвиг относительно информационной плоскости (AN-65)

| Было (Information Plane) | Стало (Semantic Navigator) |
|--------------------------|----------------------------|
| «Где лежит файл задачи?» | «Насколько код близок к намерению?» |
| Граф зависимостей | Карта плотности смыслов + векторы «тяги» |
| Поиск по ключевым словам | Запрос по контексту, дрейфу, вакуумам |
| Агент читает весь репо | Семантически отфильтрованный контрактный срез |

**Итог навигатора:** WG из «системы учёта» → «система понимания». Главный вопрос AI-разработки: *делаем ли то, что задумали, или просто пишем код?*

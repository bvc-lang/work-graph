## Короткий ответ

**Да.** По архитектуре **WG + BVC уже образуют информационную плоскость**; сейчас она используется преимущественно как «бэклог + аудит». Если явно выделить навигационный слой, получится карта намерений, исполнения и доказательств, по которой могут перемещаться и люди, и агенты.

---

## Что такое «информационная плоскость» в контексте WG

Это не плоский список задач и не база знаний. Это **многомерный граф с контрактами**, где:

| Измерение | Что описывает | Пример в WG |
|-----------|---------------|-------------|
| **Семантика** | О чём намерение | BVC: `Basis/Vector/Goal`, теги, домен (1С/OneBase) |
| **Топология** | Как связано | `depends_on`, `implements`, `verified_by`, `traces_to_code` |
| **Состояние** | Где находится | `todo → ready → doing → done/blocked`, `tier A/B/C` |
| **Доказательность** | Насколько подтверждено | `evidence[]`, `gate_status`, `audit_trail` |
| **Время** | Когда произошло | `created_at`, `completed_at`, коммиты, версия схемы BVC |

Навигация по такой плоскости — это не «поиск по тексту», а **запрос к контрактам и связям** с возможностью движения по рёбрам графа.

## Как уже можно навигировать (базовый слой)

| Механизм | Что делает | Где живёт |
|----------|------------|-----------|
| `get_unified_linkage(work_id)` | Возвращает все связи атома: зависимости, код, доказательства, родительские эпики/AN | MCP / runtime |
| `get_pvrg_task_scope` | Даёт контекст задачи: цели, ограничения, запрещённые паттерны | MCP |
| `get_graph_rag_context` | Семантический срез: похожие закрытые задачи, прошлые решения, audit-след | MCP |
| `list_evidence_records({ filters })` | Фильтрация доказательств по типу, задаче, дате, tier | MCP |
| UI-проекции | Доска (статусы), Проверки (гейты), Память (аудит), Аналитика (AN-иерархия) | Dashboard |

**Это уже навигация**, но она размазана по разным инструментам и не оформлена как единый «слой перемещения по плоскости».

## Что добавить, чтобы плоскость стала явной

### 1. Единый навигационный API (MCP)

```json
// query_intent_plane(query)
{
  "startNode": "implement-trace-links-v1",
  "direction": "upstream",
  "filters": { "tier": "A", "status": "done", "domain": "1C" },
  "depth": 2,
  "returnFormat": "graphml | json | markdown"
}
```

Направления:

- `upstream` — от кода к намерению (`file → work → epic → AN`)
- `downstream` — от намерения к последствиям (`AN → epic → work → evidence → deploy`)
- `lateral` — соседние задачи по семантике/зависимостям
- `temporal` — состояние плоскости на дату X (аудит-слайдер)

### 2. Материализованные индексы (runtime)

Граф растёт → запросы тормозят. Нужно:

- **Семантический индекс** по BVC-тексту + evidence (вектор + keyword)
- **Индекс зависимостей** (precomputed adjacency list)
- **Снимки состояний** (`snapshot@<date>`) для temporal-навигации

### 3. Визуализация + интерактив

- **Граф-вью:** узлы = BVC-атомы, рёбра = связи, цвет = tier/status, размер = количество evidence
- **Временная шкала:** прокрутка по коммитам/закрытиям, подсветка изменений контрактов
- **Контекстная панель:** при клике на узел — `get_work_contract`, `evidence`, `audit_trail`

### 4. Навигация для агента (ограниченная, но безопасная)

Агент не должен «блуждать» по плоскости. Навигация для него — контрактная:

```
agent → query_intent_plane({ start: "current_task", direction: "upstream", depth: 1 })
      → получает контекст намерения и прошлые решения
      → работает в рамках allowed scope
      → фиксирует новое ребро produces_evidence
```

См. также [AN-57](agent-session-warmup-vs-enforcement.md) (scope / enforcement).

## Примеры навигационных сценариев

| Роль | Запрос | Что получает |
|------|--------|--------------|
| **Архитектор** | Все задачи tier A, где validation упал за последний спринт | Список `work.id` + `evidence.fail` + ссылки на `AN` с разбором |
| **Разработчик** | Что блокирует `implement-onebase-report`? | Цепочка `depends_on` → задача в `blocked` → причина в evidence |
| **Аудитор** | Экспорт плоскости на 2026-05-01 | `snapshot@2026-05-01` в JSON/GraphML + audit trail |
| **Агент (Cursor)** | Контекст для `fix-trace-drift` | `get_graph_rag_context` → прошлые решения, запрещённые паттерны, связанные файлы |

## Границы и anti-goals

| Не делать | Почему |
|-----------|--------|
| Превращать в «универсальную базу знаний» (Notion/Obsidian) | WG — плоскость **рабочих артефактов + доказательств**, не хранилище заметок |
| Давать агенту свободный обход графа | Навигация агента должна быть ограничена контрактом задачи (`allowed scope`) |
| Строить глобальный граф across repos | Фокус — один репозиторий = одна плоскость. Кросс-репо связи — опционально, через federation |
| Требовать realtime-обновление UI при каждом коммите | Плоскость обновляется через `bvc:lint` + `verify` pipeline; UI читает снимки/проекции |

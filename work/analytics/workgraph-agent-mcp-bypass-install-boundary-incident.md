# AN-77: Агент обошёл Work Graph MCP и изменил канон напрямую

Дата: 2026-06-05

**Запрос:** по текущему инциденту проанализировать реализацию; если Work Graph будет устанавливаться в папку проекта, проверить риск прямых правок агентом вместо общения через MCP; оценить вариант `.workgraph` или отдельной папки установки и записать разбор в аналитику.

## Запрос

Разобрать текущий инцидент: агент сначала сделал реализацию, затем вручную создал задачу, вместо того чтобы идти через разбор -> `create_work_item` -> выполнение -> доказательство -> закрытие. Отдельно проверить риск для сценария, где Work Graph устанавливается в папку пользовательского проекта: не будет ли агент точно так же общаться с Work Graph не через MCP, а прямыми правками файлов.

## Что произошло в инциденте

В ходе задачи про ползунок масштаба шрифта агент:

1. записал разбор в `work/analytics/font-scale-settings-reference-masterclick.md`;
2. сразу изменил UI-файлы и тесты;
3. перезапустил UI;
4. только после замечания оператора создал work item;
5. сначала создал work item вручную через файловую правку, затем после повторного замечания перечитал правила и пересоздал его через MCP `create_work_item`.

Это не баг UI и не баг формата `.work.bvc`. Это сбой границы исполнения: агент имел доступ к файлам канона и использовал общий файловый инструмент вместо штатного Work Graph write API.

## Почему правила не сработали

Правила уже есть, но они в основном мягкие:

- `docs/cursor-rules/agent-workgraph-single-backlog.mdc` говорит, что новая инициатива из analytics должна идти через `create_work_item`, а статус по умолчанию должен быть `backlog`.
- `docs/cursor-rules/work-items-russian.mdc` и `work-item-bvc-quality.mdc` требуют русские развёрнутые секции и явные анализ/решение.
- `packages/workgraph-mcp/src/prompts.mjs` описывает tool workflow: `create_work_item`, затем анализ/решение, затем evidence/complete.

Но Cursor-агент в обычном режиме всё равно имеет файловые инструменты. Если он не вызвал MCP prompt/tool сам, hard gate нет: `intent/**/*.work.bvc` выглядит как обычный файл, который можно создать или отредактировать через `ApplyPatch`.

Итог: Work Graph защищает канон на уровне **процесса и lint**, но не на уровне **write boundary**.

## Риск при установке Work Graph в проект

Да, риск повторится в пользовательском проекте, если Work Graph ставится так, что канон лежит рядом с кодом и открыт для обычных файловых правок.

Текущая per-project модель делает следующее:

- создаёт `intent/`, `charter/`, `architecture/` в корне проекта;
- создаёт `.work-graph/config.json`, `.work-graph/run-ui.mjs`, `.work-graph/run-mcp.mjs`;
- добавляет npm-скрипты `workgraph:ui`, `workgraph:mcp`;
- добавляет `.cursor/mcp.json` с `@work-graph/mcp`;
- может добавить `.cursor/rules/work-graph-project.mdc`.

Эта модель хороша тем, что канон едет в git вместе с проектом. Но с точки зрения агента это всё ещё обычные файлы в рабочей директории. Если агенту доступен `ApplyPatch`, он может создать `intent/ui/dashboard/work/foo.work.bvc` напрямую, минуя `create_work_item`.

## Отдельная проблема: Work Graph управляет разработкой самого себя

Текущий инцидент сильнее обычного per-project риска, потому что Cursor открыт в папке самого Work Graph: `D:\Work\IDE\work graph`.

В одном workspace одновременно лежат:

- код движка Work Graph (`src/`, `packages/`, `scripts/`);
- канон управления этим же движком (`intent/`, `work/analytics-records.jsonl`, `work/analytics/`);
- правила для агента (`docs/cursor-rules/`, частично `.cursor/rules/`);
- MCP-сервер, который должен быть единственным write API для work items.

Это self-hosting без изоляции. Агент видит `intent/**/*.work.bvc` не как удалённый управляющий контур, а как соседние файлы рядом с `src/workGraphBacklogUiServer.mjs`. Поэтому при давлении "быстро исправить" он естественно использует самый короткий путь: `ApplyPatch` по коду и затем `ApplyPatch` по задаче.

Для обычного проекта проблема будет похожей, но менее острой: Work Graph будет внешним инструментом, а канон проекта — control-plane папкой. В текущем WG-repo граница совсем размыта, потому что продукт разрабатывает собственный runtime, UI, MCP и backlog в одном дереве.

Практический вывод: self-hosted режим должен быть помечен как повышенно опасный. Для разработки самого Work Graph нужен либо отдельный "host workspace" для управления, либо жёсткое правило: в репозитории WG канон тоже read-only для file tools, а все изменения work items идут только через MCP/CLI.

## Что даёт `.workgraph` / `.work-graph`

Перенос канона из корневых `intent/`, `charter/`, `architecture/` в отдельную папку вроде `.workgraph/` или `.work-graph/canon/` снижает шум в проекте и делает границу заметнее:

```text
my-project/
  src/
  package.json
  .work-graph/
    config.json
    run-ui.mjs
    run-mcp.mjs
    canon/
      intent/
      charter/
      architecture/
```

Плюсы:

- проще объяснить: всё, что внутри `.work-graph/canon`, меняется только через Work Graph tools;
- проще настроить Cursor rule и будущий hook: запрет прямой записи в `.work-graph/canon/**`;
- меньше смешения задач WG с прикладным кодом проекта;
- легче сделать отдельный режим упаковки/миграции канона.

Минусы:

- hidden-папка хуже видна человеку и может быть случайно добавлена в `.gitignore`;
- ломается текущая привычка и часть tooling, где `intent/index.bvc` лежит в корне;
- агент всё равно технически сможет править `.work-graph/canon/**`, если нет hard gate;
- перенос папки сам по себе не заставляет использовать MCP.

Вывод: `.workgraph` помогает как **организационная граница**, но не решает главный инцидент без запрета прямой записи.

## Отдельная папка установки движка

Отдельная установка движка уже частично выбрана в npm-first модели:

- движок идёт через `node_modules/@work-graph/*`;
- пользовательский проект хранит только config, runners и канон;
- dev-first override возможен через `WORKGRAPH_ENGINE_ROOT`.

Это правильное направление: исходники Work Graph не должны копироваться внутрь проекта. Но отдельный движок решает другую проблему — обновление и дублирование кода WG. Он не решает прямую правку work items, потому что канон всё равно должен жить в проекте и быть доступен агенту.

## Вариант: отдельная установка Work Graph + переключение проектов в UI

Более сильная модель изоляции: Work Graph устанавливается не внутрь каждого проекта, а как отдельный локальный управляющий хост. В UI оператор добавляет проекты, а Work Graph читает их канон по зарегистрированным путям:

```text
work-graph-host/
  src/ или node_modules/@work-graph/*
  ~/.work-graph/workspaces.json

project-a/
  src/
  .work-graph/canon/ или intent/

project-b/
  src/
  .work-graph/canon/ или intent/
```

В этом варианте Cursor может быть открыт в `work-graph-host` для разработки WG или в `project-a` для прикладной разработки, но UI Work Graph живёт как отдельный процесс и умеет переключать активный проект. Это снижает смешение "код движка" и "канон управляемого проекта".

Плюсы:

- один UI и один порт для нескольких проектов;
- код Work Graph физически отделён от прикладных репозиториев;
- проще сделать project switcher: active workspace задаёт `repoRoot`, а не требует перезапуска UI;
- можно держать канон проектов в их git-репозиториях, но не смешивать его с исходниками самого WG;
- для self-hosting можно открыть UI-хост отдельно, а разработку движка вести как один из зарегистрированных проектов.

Минусы:

- появляется реестр проектов (`~/.work-graph/workspaces.json`) и UX добавления/удаления проекта;
- нужно строго параметризовать UI/MCP по `repoRoot`, чтобы ни один слой не читал неявный cwd;
- агент в проекте всё равно сможет править локальный канон напрямую, если в этом проекте нет запрета file-write;
- оператору нужно понимать разницу между "WG host" и "проектом, которым WG управляет".

Эта модель лучше решает текущий self-hosting-инцидент, чем простой перенос канона в `.workgraph`. Она отделяет control-plane UI от репозитория движка и делает переключение проектов явной операцией. Но она всё равно должна сочетаться с write-boundary: UI переключает проект, MCP пишет задачи, прямой patch канона запрещён.

Целевая схема для UI:

1. В шапке или сайдбаре есть текущий проект: имя, путь, git branch.
2. Dropdown "Проекты" показывает зарегистрированные корни.
3. Переключение вызывает API уровня `/api/workspace/switch`, после чего все snapshot/read/write операции используют новый `repoRoot`.
4. MCP-сервер получает тот же `repoRoot` из registry или запускается per-project с `WORKGRAPH_ROOT`.
5. В каждом проекте хранится только канон и минимальный `.work-graph/config.json`; движок не копируется.

Вердикт по варианту: для обычного пользователя основной путь может остаться per-project install, но для разработки самого WG и для нескольких похожих проектов нужен отдельный WG host с переключателем проектов. Это должен быть не "копировать WG в каждый проект", а "один управляющий процесс, много repoRoot".

## Рекомендация

Нужно разделить две границы:

1. **Граница установки движка:** движок отдельно от проекта. Основной путь — npm packages или общий host; не копировать репозиторий Work Graph в проект.
2. **Граница записи канона:** work items и evidence нельзя менять обычными file edits; только через MCP/CLI API, кроме специальных migration scripts.

Лучший вариант для следующего шага:

- оставить npm-first установку движка;
- рассмотреть перенос канона в `.work-graph/canon/` или `.workgraph/` как явную control-plane папку;
- отдельно описать self-hosted режим WG: код движка и управляющий канон нельзя считать одной обычной кодовой областью;
- для self-hosting и нескольких проектов вернуть в фокус отдельный WG host с переключателем проектов в UI;
- ввести правило/hook/lint, который ловит прямые изменения `intent/**/*.work.bvc` или `.work-graph/canon/**/*.work.bvc`, если они не сделаны через Work Graph tool;
- в Cursor rule проекта явно написать: "файлы канона read-only для агента; create/update/complete только через MCP";
- в `create_work_item` и `complete_work_item` добавлять машинный след вроде `work.updated_by: workgraph-mcp` или structured audit record, чтобы отличать штатную запись от ручного patch.

## Минимальный продуктовый вывод

Перенос в `.workgraph` полезен, но не как замена MCP. Без write-boundary агент всё равно сможет открыть скрытую папку и отредактировать `.work.bvc` напрямую.

Главная защита должна быть не "куда положить файлы", а "какой путь записи считается допустимым":

- читать канон можно как файлы;
- писать канон можно только через Work Graph MCP/CLI;
- прямые file edits допускаются только для миграций с явным скриптом и отдельным evidence.

## Что изменить в модели установки

Для нового проекта стоит целиться в такую структуру:

```text
my-project/
  src/
  package.json
  .cursor/mcp.json
  .cursor/rules/work-graph-project.mdc
  .work-graph/
    config.json
    run-ui.mjs
    run-mcp.mjs
    canon/
      intent/index.bvc
      intent/**/work/*.work.bvc
      charter/
      architecture/main.bvc
```

Но мигрировать текущие проекты стоит только после отдельного ADR, потому что это затронет UI, MCP, CLI, тесты и документацию.

## Вердикт

Инцидент подтверждает риск: если канон Work Graph находится в рабочем дереве проекта и агент имеет обычные file-write tools, он может обойти MCP и нарушить workflow.

В self-hosted режиме риск максимальный: Work Graph разрабатывает сам себя, и агент видит управляющие `.work.bvc` рядом с кодом движка.

Создание `.workgraph` или `.work-graph/canon` улучшит UX и видимость границы, но недостаточно само по себе. Нужен hardening: проектные rules, MCP-first write path, audit marker и lint/hook против прямых изменений канона.

Отдельная установка WG с переключателем проектов в UI выглядит лучшим направлением для self-hosting и multi-project работы: один управляющий хост, много подключённых `repoRoot`, а канон каждого проекта остаётся рядом с его кодом.
